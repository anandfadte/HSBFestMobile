
ZENITH '26
College Fest Management System
A Vibe-Coding Capstone Assignment — PM2-01 & PM2-02
HSB — Product Management II: Technology & Agile Execution
1. Overview
This assignment asks students to build a small, genuinely working product — not a mockup, not a slide — using an AI coding assistant (“vibe coding”). The project is a College Fest Management System called Zenith '26: a student-facing event portal plus an admin dashboard, built on a real client-server architecture with a real database.
The point isn't to turn PM students into engineers. It's that every concept from PM2-01 (How Software Works) and PM2-02 (Front-End, Back-End & Mobile) stops being an abstraction the moment a student has to watch their own API return a 404, fix a validation bug, or explain why the admin dashboard's numbers are always correct even when two people register at the same second. Vibe coding makes that possible without requiring a semester of programming first — the student directs, reviews, and tests; the AI assistant (Antigravity) writes the code.
2. Learning Objectives
By the end of this assignment, a student should be able to point to a specific screen or line of their own project and explain:
Client vs. server — which half of their app is the “client” and which is the “server,” and why the server, not the browser, is the one source of truth.
The three-layer stack — where the client layer, server layer, and data layer live in their own project, literally in different files.
The request lifecycle & HTTP — what a GET and a POST actually do, and what a 200, 400, 404, and 409 status code each mean, because they will have triggered all four themselves.
API contracts — why the frontend and backend had to agree on exact endpoint shapes before either could be built, and what breaks when that contract isn't respected.
“Never trust the client” — by implementing the same validation rule twice (once in JavaScript, once in FastAPI) and seeing why the second copy is the one that actually protects the data.
Databases — by designing a schema, seeding it with real data, and watching registrations persist across a server restart.
Vibe coding as a PM skill — directing an AI coding tool in small, testable increments, reading its output critically, and writing precise bug reports instead of vague ones.

A note on the Tailwind CDN
Tailwind's browser-based Play CDN (used in this project) is convenient for local classroom practice but is meant for development, not production, and it requires internet access. For an offline workshop, switch to a compiled stylesheet or a local copy of Tailwind instead.
5. The Project: What Zenith '26 Looks Like
These are the design direction for the three core screens — not screenshots of a pre-built application. Students build these themselves, screen by screen, using the companion prompts file.
Screen 1 — Student Event Portal
Event cards, search, category filters, event details, available seats, and a registration form.
Screen 2 — Admin Dashboard

Screen 3 — Registration Experience
A responsive event detail view, input validation (client-side and server-side), a clear registration confirmation, and clear error messages when something goes wrong (event full, already registered, missing fields).
6. Architecture
The architecture is deliberately simple — one backend application, one database file, no cloud dependency:



The whole system in one line
Browser (HTML + Tailwind + JavaScript)  — HTTP requests / JSON responses →  FastAPI (serves both the frontend files and the REST API)  — SQL queries →  SQLite (fest.db, a single local file)

Everything runs on the student's own laptop during the workshop. As a stretch idea for a later course module, the same FastAPI backend could power a native Android app built with Kotlin and Jetpack Compose — the web app and the Android app would share one backend and one API contract, which is itself a good live example of the “API contracts” lesson from PM2-02.

A deliberate design choice worth discussing in class
available_seats is never stored as its own column. It's computed on every request as capacity minus a live COUNT of registrations. Storing a separate “seats left” number would create two sources of truth that can drift out of sync — exactly the kind of data-consistency bug PM2-01's “three layers” lesson warns about. Ask students what could go wrong if they ‘optimized’ this by caching the count instead.

10. How to Use the Vibe-Coding Prompts File
The companion file, Vibe-Coding-Prompts-Zenith26.md, contains one ready-to-paste prompt per build step above, written for Google Antigravity. A second companion file, events_seed.xlsx, holds the 14 seed events as data rather than as text in a prompt. Students should:
Open Antigravity and create the project folder described in Step 0.
Copy events_seed.xlsx into that project's data/ folder, as Step 0 instructs — Step 1 cannot seed the database without it.
Copy one step's prompt block at a time into Antigravity's agent chat — never multiple steps at once.
Run the app after every step and actually look at it before moving on.
When something looks wrong, describe what they observed in plain language (“the register button does nothing and the console shows a 404”), not a guess at the cause — and let Antigravity fix it.
Keep the prompts file open the whole session as a checklist.
This is the actual skill being taught: a PM directing an engineering tool in small, verifiable increments, rather than either writing all the code by hand or blindly accepting a huge, unreviewed change.
11. Testing with Postman
Install the Postman desktop app (free; no account needed for local testing — its API Client works signed out).
Import the zenith26-api.postman_collection.json file generated in Step 10 of the prompts file.
With the FastAPI server running locally, run each request in the collection in order.
For every response, read the status code first, then the body — don't just check “did it look okay in the browser.”
Run the deliberately-invalid registration request and confirm a 400 comes back with a clear error message, not a server crash.
Register the same email twice for the same event and confirm a 409 comes back the second time.
This is the step where students stop trusting “the UI looks like it worked” and start reading the API contract directly — exactly the muscle the PM2-02 “API Contracts” lesson was building toward.
A third companion file, Postman-Testing-Commands-Zenith26.md, spells out all 18 of these requests with exact bodies and expected responses, plus Postman desktop setup steps — use it as the checklist for this section.

15. Troubleshooting / FAQ
“uvicorn: command not found” or Python errors on startup
The virtual environment from Step 0 probably isn't activated. Ask Antigravity to show the exact activate command for the student's OS and run it before starting the server again.
“Address already in use” on port 8000
A previous server instance is still running. Close that terminal window or ask Antigravity to stop the running process before restarting.
The page loads but no events appear
Open the browser console (F12) and check for a failed request to /api/events. Most often this means the backend isn't running, or the frontend is pointed at the wrong URL.
“Antigravity generated something I don't understand — what do I do?”
Ask it to explain the specific function or file in plain language before moving on. Understanding what was built is part of the assignment, not optional — a PM who can't explain their own demo hasn't learned the lesson.
